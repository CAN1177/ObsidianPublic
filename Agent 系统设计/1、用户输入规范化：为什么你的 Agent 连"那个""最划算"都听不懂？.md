### 一、核心概念

**用户输入规范化**（User Input Normalization）：将用户随意、口语化、不完整的输入转化为结构清晰、语义明确、可供后续意图识别和任务执行的标准化表达。

> 类比：相当于传统软件工程中的**需求分析**，是Agent系统的第一道关口。

---

### 二、六大类用户输入问题（附典型例子）

| 大类 | 核心特征 | 典型例子 |
|:---|:---|:---|
| **指代问题** | 用代词/序数词代替具体对象 | "第二个适合生产吗？""刚才那个项目怎么包装？" |
| **缺失问题** | 缺少主语、宾语、约束条件等 | "市场占有率多少？""帮我优化一下。" |
| **表达问题** | 口语化、跳跃、病句、临时改口 | "不是，我说的是另一个""这个不太行，换个更像面试能讲的" |
| **词义问题** | 非标准术语、同义词、黑话、多义词 | "RAG/检索增强/知识库""抓手/不够P8" |
| **主观判断问题** | 依赖个人偏好、场景标准的判断词 | "哪个最有性价比？""再高级一点。" |
| **外部事实问题** | 需实时数据/检索/工具才能确定 | "最近哪个框架更火？""现在最便宜的是哪个？" |

### 四、处理时机选择（三层架构）

```
┌─────────────────────────────────────────┐
│  时机1：意图识别之前  ← 推荐（通用/C端Agent） │
├─────────────────────────────────────────┤
│  时机2：和意图识别一起   （领域专属Agent）    │
├─────────────────────────────────────────┤
│  时机3：ReAct执行循环中  （复杂依赖型，必选）  │
└─────────────────────────────────────────┘
```
![[Pasted image 20260803150219.png]]
**最佳实践：1/2 + 3 结合使用**
- **初步处理**：解决80%常见问题（指代消解、省略补全、病句修正）
- **深度处理**：解决依赖上下文/工具调用的复杂情况（如"最有性价比"需查询后量化）

### 五、Prompt撰写三大要点

#### 5.1 明确职责边界（能做 vs 不能做）

| ✅ 能做什么 | ❌ 不能做什么 |
|:---|:---|
| 指代消解 | 不直接回答用户问题（最易犯）|
| 省略句补全 | 不执行工具 |
| 病句修正 | 不做最终推荐 |
| 术语标准化 | 不判断业务意图 |
| 黑话解释 | 不生成完整方案 |
| 多义词消歧 | 不擅自补充事实 |
| 判断是否需要澄清 | 不强行猜测低置信内容 |
| 判断是否需要搜索 | 不伪造实时信息 |

#### 5.2 Few-Shot示例设计

**经济型方案**：线上运行时自动收集"古怪输入→规范输出"作为案例库

**进阶方案**：用检索机制从大量案例库中动态选取最相关的few-shot注入Prompt

#### 5.3 完整性检查清单

- [ ] 主谓宾是否完整
- [ ] 代词是否完全消解（输出**代词消解表格**）
- [ ] 形容词/极值是否已"可量化"

**代词消解表格示例：**
```
"第一个方案" → "使用TCC的方案，命名为TCC方案"
"那个帅气的同事" → "邓大明"
```

### 六、进阶优化技巧

#### 6.1 命名策略（预防性设计）
- ❌ 差："方案一""方案二" → 用户后续说"方案一"易混淆
- ✅ 优："TCC方案""Saga方案" → 用户自然用特定名称引用

> **本质**：按名索引，规避大模型推理阶段的引用错误

#### 6.2 澄清机制
- 代词消解推断不出时，**主动要求用户澄清**，而非瞎猜

#### 6.3 结构化输出
- 主谓宾字段 + 定状补解释
- 对"性价比"等词输出量化标准

### 八、两大高阶案例（面试加分项）

#### 案例A：基于属性+检索的推理（长周期指代消解）

**场景**：假期前推荐"鸡鸣寺看樱花" → 假期后说"你上次推荐的看樱花的那个地方……"

**难点**：时间跨度长 + 属性指代（"看樱花的地方"而非简单"那个"）

**两步方案**：
1. **检索召回**：用"樱花、旅游"关键词检索历史对话细节
2. **推理消解**：大模型基于窗口内容推断"鸡鸣寺"

**补偿机制**（检索失败时）：
```
属性提取 → 工具调用（如查询用户历史推荐记录）→ 再次推理
```

#### 案例B：自迭代词汇表（行业黑话/多义词治理）

**核心结构**：
```
┌─────────────┐     ┌─────────────┐
│  公共词汇表  │  +  │  用户个人词汇表 │
│  (全系统共享)│     │  (个体/小群体) │
└─────────────┘     └─────────────┘
```

**示例**："CRM"在IT行业=客户关系管理，在医疗行业=临床研究管理

**自动沉淀规则**（可"花里胡哨"地设计）：
- 总出现次数 > 100
- 讨论人数 > 3人（判定为公共词汇）
- 连续讨论 > 10次

**流程**：离线分析多轮对话 → 标记疑似词汇 → 超阈值升级入库

### 九、关键原则：可量化

**核心洞察**：任何未量化的形容词都会导致Agent输出漂移

**电商案例深度解析**：
```
用户：推荐一条裤子
Agent：牛仔裤A ¥200，休闲裤B ¥300
用户：帮我推荐一个更有性价比的牛仔裤
```

**"性价比"的两种理解**：
| 类型 | 含义 | 工具参数示例 |
|:---|:---|:---|
| 同等价格，质量升级 | 进口改国产→大品牌改小品牌 | 价格锁定[150,200]，提升材质参数 |
| 同等质量，价格降级 | 同品牌更便宜系列 | 价格锁定[100,150]，保持品牌过滤 |

**反模式**：粗暴理解为"价格低" → 忽略质量/性能/品牌/售后 → 用户体验差

**落地**：转化为工具调用参数，如 `price_range=[150, 200]`
