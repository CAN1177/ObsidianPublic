## 一句话总纲

**流程编排解决的是「多个任务怎么衔接」：先选对工作流，把力气花在需求对齐侧，让需求实现侧退化为一句「实现已对齐的需求」，再用测试守住长期迭代。**

这条主线可以拆成三段：

1. **选工作流**（第 10 节）：不要从 0 开发，在「使用量大、结构简单、模块化」的工作流上改造
2. **把需求对齐做厚**（第 11–18 节）：Superpowers 舍弃了偏差把控，Matt 靠 Grilling 及其四条优化把偏差控制住
3. **让实现变薄但可验证**（第 19–20 节）：不用盯实现过程，但要盯测试用例；用三位一体流程生成能准确校验需求的测试

# 第一部分：选工作流

## 第 10 节 · 流程编排概览（`a/9`）

### 核心结论

`AI 编程工作流`由多条软件开发相关的工作流组成（需求开发、修复 Bug、系统重构、线上监控），每条工作流以 `Skill` 形式编排 1 到多个步骤，每个步骤对应 `AFK` 或 `HITL` 一种工作模式（参考：[工作流的构成](https://iamkasong.com/course/a/9#kj2)）。

**不要从 0 开发自己的工作流**，而是在同时满足三个条件的工作流基础上改造（参考：[选择 AI 编程工作流](https://iamkasong.com/course/a/9#i1J)）：

| 条件 | 为什么 |
| --- | --- |
| **使用量大** | Skill 是自然语言写的，形式化程度、可判定性都比程序语言松散、更难测试。使用量大意味着效果经受过广泛测试，更稳定 |
| **结构简单** | 结构越复杂，你越不知道稳定的效果来自哪里——是 Skill 好、编排好，还是 Skill 与脚本配合巧妙。变数越多，自定义时不确定性越大 |
| **模块化** | 效果已经过考验的**原子 Skill** 可以重新组装，大概率效果不错 |

（参考：[三个条件的解释](https://iamkasong.com/course/a/9#R1k)）

### 关键观念

**选择是一次性的，迭代是长期的。** Agent Harness 优化、模型智力提升、上下文窗口变大都会让最佳实践变化，所以流程编排的最佳实践始终在变（参考：[章节概览](https://iamkasong.com/course/a/9#60-)）。本章的任务是演示工作流**进化的完整过程**，而不是给一个定论。

### 关键术语

- **AI 编程工作流**：把软件开发任务组织成多个步骤，并为每步选择 AFK、HITL 或组合的流程，通常由 Skill 构成
- **原子 Skill**：从复杂 Skill 中拆出的功能更纯粹、可复用的 Skill

## 第 11 节 · 从 Superpowers 聊起（`a/a`）

### 核心结论

Superpowers 的需求开发工作流是 5 步（参考：[需求开发工作流](https://iamkasong.com/course/a/a#0YZ)）：

1. **brainstorming**（HITL）：头脑风暴对齐需求
2. **Spec**（AFK + HITL 门禁）：写设计文档，自审为通过条件，用户批准后进入下一步
3. **writing-plans**（AFK + HITL 门禁）：把设计文档拆成精确到文件、代码、测试命令的子任务
4. **implement**（AFK，遇疑问切 HITL）：`subagent-driven-development` 每个子任务一个「实现＋审查＋修复」的 AFK；或 `executing-plans` 顺序执行全部子任务后统一审查
5. **finishing-a-development-branch**：处理合并、PR、保留或丢弃分支

### 设计理念与代价

**设计理念是「完整的 AI 软件开发方法论」，把复杂度收敛到方法论内部，上手门槛极低**（参考：[设计理念](https://iamkasong.com/course/a/a#H9X)）。

- 宏观上，使用者不用知道该调用哪个工作流，Skill 内部知道该调用谁（参考：[宏观设计层面](https://iamkasong.com/course/a/a#UNP)）
- 微观上，brainstorming 的假设是「你只有模糊的想法，Agent 就想法给你指方向」，像在陌生城市问路，沿途只走一条主路，很多岔路没有探索（参考：[brainstorming 的假设](https://iamkasong.com/course/a/a#pp8)）

**代价**：这么做是为了减少提问次数、降低上手门槛，等于**舍弃对偏差的把控，换取更少的注意力投入**（参考：[Superpowers 的取舍](https://iamkasong.com/course/a/a#lqT)）。

### 连锁反应（重点）

未知不会凭空消失。对齐阶段没填补的未知，实现阶段由 Agent 自行填补——所以 `writing-plans` 会把任务细化到具体命令（参考：[工作流的取舍](https://iamkasong.com/course/a/a#f5B)）。

但**实现前很难预估具体命令和方法**，只有做到那一步才知道（比如项目惯例是驼峰命名，`calculate-completion.ts` 该叫 `calcDone.ts`）（参考：[过早细化的隐患](https://iamkasong.com/course/a/a#Oed)；[命名惯例的例子](https://iamkasong.com/course/a/a#YG9)）。

于是产生**两个层面的不对齐**：

1. 真实需求 ↔ 实现计划（Agent 自行填补了未知）
2. 实现计划 ↔ 实际代码（只有做到才知道具体实现）

`subagent-driven-development` 因此在每个任务后做两类审查纠偏：设计文档审查（对治不对齐 1）、代码质量审查（对治不对齐 2）。这是标准的 AFK 应用——靠**约束**降低偏差（参考：[两层不对齐与两类审查](https://iamkasong.com/course/a/a#FQf)）。

## 第 12 节 · 放弃 Superpowers（`a/b`）

### 核心结论：四个角度

| 角度 | 问题 |
| --- | --- |
| **时代局限** | 25 年 10 月开源时 Agent 没有稳定的长程任务执行能力，详细步骤和逐任务审查是为了应对上下文压缩丢状态。现在 Agent 已有长程能力，这些设计变得冗余 |
| **执行耗时** | 表象是 `subagent-driven-development` 慢，本质是「每个子任务都是一个实现＋审查＋修复的 AFK」，而这是**弥补需求缺口造成的一系列连锁反应** |
| **偏差积累** | **这才是最大的问题。** 执行慢可以用并行补，但 `brainstorming` 是用 AI 的已知填补人类的未知，这正是偏差的主要来源，长期使用会加速项目腐败 |
| **不方便自定义** | Superpowers 满足「使用量大」「结构简单」，但每个 Skill 比较复杂、没有模块化 |

（参考：[角度1 时代局限](https://iamkasong.com/course/a/b#KLY)；[角度2 执行耗时](https://iamkasong.com/course/a/b#jtd)；[角度3 偏差积累](https://iamkasong.com/course/a/b#bQ7)；[角度4 不方便自定义](https://iamkasong.com/course/a/b#pWG)）

**归根结底，Superpowers 在设计上没有平衡好注意力与偏差。**

### 最重要的划分与预测

把需求开发工作流拆成**需求对齐侧**与**需求实现侧**，会发现被放弃的原因主要出在**对齐侧**——执行耗时和偏差积累都源于需求缺口没被弥补；实现侧则随 Agent 发展，开发者需要额外关注的越来越少（参考：[总结与趋势预测](https://iamkasong.com/course/a/b#BIM)）。

**预测**：需求对齐侧越来越厚（逐渐进化为**系统协同平台**），需求实现侧越来越薄（最终退化为一个 `/goal` 命令）。

## 第 13 节 · 介绍 Matt Skills（`a/c`）

### 核心结论：5 步与差异

Matt 的需求开发工作流（参考：[需求开发工作流](https://iamkasong.com/course/a/c#0YZ)）：

1. **Grilling**（HITL）：`grill-with-docs` = `grilling`（提问涉及需求路径上所有岔路，完全对齐）+ `domain-modeling`（维护 `CONTEXT.md`、必要时记录 `ADR`）。只有完全达成共识才进下一步
2. **Spec**（AFK）：`to-spec` 消费 Grilling 结论，生成并发布规格文档
3. **Tickets**（AFK + HITL 门禁）：`to-tickets` 拆成**多个带依赖关系的子任务**，发布前过门禁
4. **Implement**（每子任务一个 AFK）：按 TDD 执行所有子任务
5. **Review**（AFK）：`code-review` 同时启动两个独立 Subagent——Standards Review 查编码规范、Spec Review 查需求遗漏／错误实现／范围蔓延（参考：[Review 阶段](https://iamkasong.com/course/a/c#qd-)）

**与 Superpowers 的表面步骤几乎一致（对齐→规格→计划→执行→审查），但区别很大**：`subagent-driven-development` 每个子任务都审查，`code-review` 是全部完成后统一审查一次。

### 两个层面的差异

**理念层面**：Superpowers 核心是**简单好上手**，Matt 完全相反。Matt 起源于作者自己的 AI 编程实践，他更在意项目是否真的适合开发者使用，所以在对齐需求上复杂得多（参考：[理念层面](https://iamkasong.com/course/a/c#35x)）。

**架构层面**：Superpowers 属于第二级「流程编排」，中间产物以**本地文档**流转；Matt 在此之上提供了向「系统协同」延伸的能力——中间产物可以呈现为**平台 Issue**（参考：[架构层面](https://iamkasong.com/course/a/c#WdT)）。

关键理解：**Issue 不是 GitHub 专属，而是通用的「记录进度、过程细节的任务管理功能」**。自己和 Agent 交接用本地文档就够；**多人类、多 Agent 交接**则需要平台 Issue。所以从本地文档到平台 Issue，是**从本地流程编排向多工种协同的迈进**。`Issue 分诊工作流`（triage）的作用就是按意图分发 Issue。

两个项目开源只间隔 4 个月，不如说是**不同时代 AI 编程工作流的最佳实践**（参考：[总结](https://iamkasong.com/course/a/c#2iQ)）。

# 第二部分：把需求对齐做厚（Grilling 与四条优化）

## 第 14 节 · Grilling 策略（`a/d`）

### 核心结论

需求对齐就是为了填补 4 类需求缺口。`Grilling`（拷问）的核心逻辑是：

> 将问题组织成一棵**设计决策树（design tree）**：每项决策都会分叉出依赖它的后续决策。持续深入地拷问用户，直到双方达成共识。

（参考：[Grilling 策略](https://iamkasong.com/course/a/d#mON)）

**完全对齐的需求是一棵树**，每个节点是一个**被填补的需求缺口**，节点间有依赖关系。以「20 分钟后提醒我关火」为例：

- 需求：担心忘记关火，20 分钟后要得到提醒
- Agent 理解：创建定时任务，20 分钟后发「请关火」通知
- 人理解：到点了有人主动提醒我
- **共同理解**：20 分钟后用户会收到明确的关火提醒 → 需求缺口被填补

（参考：[被填补的需求缺口](https://iamkasong.com/course/a/d#6ES)）

严格说完全对齐的需求应该是**图**而非树（子树节点可能依赖另一棵子树的节点），实践上简化为树已够用（参考：[树与图的简化](https://iamkasong.com/course/a/d#393)）。

### 优缺点与四条优化

- **优点**：需求完全对齐，后续实现偏差很少
- **缺点**：消耗开发者大量注意力在「一问一答填补需求缺口」上

（参考：[Grilling 的优缺点](https://iamkasong.com/course/a/d#JTj)）

优化 Grilling 的四条策略（参考：[优化 Grilling](https://iamkasong.com/course/a/d#Jqb)）：

1. 把**未知的已知**记录在文档中，Agent 直接读文档对齐 → 第 15 节
2. 从「一次问一个问题」变成「一次问一批问题」 → 第 16 节
3. 根据**需求缺口的类型**设计不同的快速对齐路径 → 第 17 节
4. 防止**已对齐的需求**因**上下文窗口**被遗忘 → 第 18 节

**内化要点**：Matt 的需求对齐之所以复杂，全部围绕同一个命题——**保持 Grilling 优点（完全对齐）的同时，减少开发者注意力的消耗**。

## 第 15 节 · 填补未知的已知（`a/e`）

### 核心结论

优化 1：把**未知的已知**（对你太显而易见、根本不会提，但看到结果能立刻判断对错的知识）写进文档，让 Agent 直接读文档对齐，不必问你（参考：[本节目标](https://iamkasong.com/course/a/e#GyI)）。

### 记录什么

**不适合记录**：Agent 能从项目中快速查到的（目录结构、代码实现逻辑）、经常变化的。
**适合记录**：用户偏好、决策、共识、项目背景、常用入口。

（参考：[什么适合被记录](https://iamkasong.com/course/a/e#pDR)）

### 什么最值得记录

《人月神话》提出**概念完整性**：系统在设计上保持一致、连贯、自洽。公式：

```text
概念完整性 = 统一的概念模型 + 一致的设计原则 + 迭代时遵守前序原则
```

（参考：[什么最值得被记录](https://iamkasong.com/course/a/e#Pp1)；[公式](https://iamkasong.com/course/a/e#-cR)）

因此最值得记录的是两类未知的已知（参考：[两类知识](https://iamkasong.com/course/a/e#IT5)）：

| 类别 | 载体 | 内容 |
| --- | --- | --- |
| **统一的概念模型** | `CONTEXT.md` | 谈到的概念的含义（统一语言） |
| **一致的设计原则** | `ADR` 文件 | 各种决策的原因 |

- **统一语言（Ubiquitous Language）**：业务专家、产品经理、开发者共同建立的准确统一的领域词汇，在讨论、需求、代码、测试和文档中持续使用。同一个词在不同上下文可以有不同含义（`Customer` 在销售上下文是签约主体，在客服上下文是提交工单的人），对齐需求要保证所有相关方**谈同一个词时是同一个含义**（参考：[统一的概念模型](https://iamkasong.com/course/a/e#70l)）
- **ADR（Architecture Decision Record）**：代码只能说明「系统最终做成了什么样」，说不出当时面对什么约束、考虑过哪些替代方案、为什么接受某些代价。ADR 记录**决策背景、最终决定、当前状态和产生的后果**；决策被推翻时旧 ADR 不删除，而是标记已废弃或被取代，保留完整决策历史（参考：[一致的设计原则](https://iamkasong.com/course/a/e#l35)；[ADR 的内容](https://iamkasong.com/course/a/e#RmU)）

### 具体实现

用 `/grill-with-docs` 而不是 `/grilling`：本质是 **在 `/grilling` 的同时用 `/domain-modeling` 记录上述两类知识**（参考：[具体实现](https://iamkasong.com/course/a/e#Yqz)）。统一语言存 `CONTEXT.md`，每条 ADR 一个独立文件放在 `docs/adr/`（参考：[目录结构](https://iamkasong.com/course/a/e#C2Z)）。

## 第 16 节 · BFS 需求对齐策略（`a/f`）

### 核心结论

优化 2：从「一次问一个问题」变为「一次问一批问题」。**之所以可行，是因为需求缺口之间存在依赖关系**（参考：[本节引入](https://iamkasong.com/course/a/f#o86)）。

以这棵树为例（B 依赖 A，D、E 依赖 B）：

```text
      A
     / \
    B   C
   / \
  D   E
```

- `DFS` 前序：A → B → D → E → C，**5 轮**
- `BFS`：A → B C → D E，**3 轮**，且不破坏依赖关系

（参考：[树的遍历](https://iamkasong.com/course/a/f#wwd)；[BFS 遍历](https://iamkasong.com/course/a/f#Ccq)）

**前沿（frontier）**：所有前置条件都已确定的决策，也就是现在便能提出、无须猜测尚未获得答案的问题。每轮一次性问完整个前沿：给每个问题编号并给出推荐答案，等用户回答后再进下一轮（参考：[Grilling 的核心实现](https://iamkasong.com/course/a/f#wqZ)）。

### 第二个好处：防止陷入局部需求缺口

BFS 不只减少轮次，还**提供更宏观的视野**（参考：[防止陷入局部需求缺口](https://iamkasong.com/course/a/f#L6H)）。

反例：做「销售会议录音自动整理成跟进邮件」的工具，DFS 可能先进「上传录音」这个局部缺口，一路深入上传按钮、拖拽、进度、重试——最后才发现销售根本不愿手动上传，录音本来就存在飞书会议里，前面的设计全部失效。

BFS 会先把同一层缺口摊开，你立刻能看出**不同缺口适合不同的对齐策略**：

```text
                    自动生成跟进邮件
                           │
          ┌────────┬───────┼─────────┬────────┐
        交互缺口  效果缺口 技术缺口  合规缺口    目标缺口
          │        │       │         │        │
        做原型   生成样例  Grilling  确认政策    访谈
```

（参考：[缺口分类示意](https://iamkasong.com/course/a/f#6Ge)）

### 进阶：用 AFK 生成整棵树

Grilling = 人与 Agent 就一棵需求树做 BFS 遍历。之所以要遍历每个节点，是因为漏掉的节点会在实现阶段变成偏差（参考：[进阶使用](https://iamkasong.com/course/a/f#Zmf)）。

若还想更快，可以针对需求设计一个 `AFK`，让 Agent 对需求 Grilling 直到「通过（需求树对齐）／退出（缺口无法填补）」，产出 `PRD`。这份 PRD 就是一棵树，你可以对未对齐节点继续对齐、对不满意的剪枝、对有偏差的修正——**把「逐步迭代出一棵树」变成「对完整的树进行迭代」**。

可行的两个前提：

1. 项目已迭代一段时间，有约定俗成的文档、架构、代码供 Agent 参考（积累了更多已知，Agent 不用猜）
2. AFK 的目标、通过条件、退出条件设计合理（应围绕「Agent 能否对齐 4 类需求缺口」设计）

## 第 17 节 · 需求缺口分类处理（`a/g`）

### 核心结论：四类缺口，四条路径

| 缺口类型 | 含义 | 对齐路径 | Matt 工具 |
| --- | --- | --- | --- |
| **已知的已知** | 你明确告诉 AI 的 | **Grilling**（主流程） | `grilling` |
| **已知的未知** | 你不明白，但知道自己不明白 | **调研** | `/research`、`/handoff` |
| **未知的已知** | 太显而易见不会提，看到结果能判断 | **原型** | `/prototype` |
| **未知的未知** | 没考虑过，也不知道自己缺 | **领域知识** | `/to-questionnaire` |

（参考：[已知的已知](https://iamkasong.com/course/a/g#aOp)；[已知的未知](https://iamkasong.com/course/a/g#Mhy)；[未知的已知](https://iamkasong.com/course/a/g#lvX)；[未知的未知](https://iamkasong.com/course/a/g#GzP)）

**四条路径的细节**：

- **已知的已知**：不要被动做选择题，应**主动提供更多已知的已知**，能加速 Grilling
- **已知的未知**：**不要继续 Grilling**（防止陷入局部缺口），而是开新 session 用 Deep Research 或 HITL 调研。流程是 session1 `/handoff` 总结 → session2 学习并讨论方案 → 再 `/handoff` 总结 → 回到 session1 交给 Grilling
- **未知的已知**：针对**逻辑缺口**（系统在特定环节怎么运转）和 **UI 缺口**（用户在特定场景怎么看和操作），做可视化原型直观比较（如退款详情页三种方案切换比较），结论经 `/handoff` 传回
- **未知的未知**：需要领域专家。两种方式——用**统一语言**对齐术语，或用 `/to-questionnaire` 生成问卷（发给谁、要对方提供什么、需要撰写的内容），结果给到 Grilling

### 两个启示

1. **思路要打开**：4 类缺口不只 4 种填补方式，可按业务定制。原则只有一条——**主流程通过 Grilling 驱动，不同需求缺口对应不同填补方式**
2. **视角转变**：开发者视角是「遇到缺口再填补」；**项目视角是「主动填补缺口」**——把任务主动分发给不同角色，让领域专家工作流的产物主动进入开发者的需求开发工作流。这就上升到了**系统协同**

（参考：[总结与两个启示](https://iamkasong.com/course/a/g#BIM)）

## 第 18 节 · 防止对齐被遗忘（`a/h`）

### 核心结论

优化 4：防止已对齐的需求因**上下文窗口**被遗忘。两个窗口概念（参考：[本节引入](https://iamkasong.com/course/a/h#oyy)）：

- **宣称窗口**：模型能「塞进去」的最大 token 数
- **有效窗口**：模型在真实任务中仍能保持较高准确率、可靠推理和检索的 token 数

**宣称窗口的影响**：快用尽时触发 `compact`（上下文压缩）。若在需求对齐中触发，**已填补的需求缺口的细节会丢失**，丢失的细节经 Spec、Plan、Implement 不断**放大成偏差**（参考：[宣称窗口的影响](https://iamkasong.com/course/a/h#NuO)）。

**有效窗口的影响**：一是很多模型宣称窗口本身虚标，二是有效窗口受任务复杂度影响（参考：[有效窗口的影响](https://iamkasong.com/course/a/h#Bvo)）：

| 任务类型 | 有效窗口约为宣称值 |
| --- | --- |
| 简单检索 | **50–70%** 甚至更高 |
| Multi-hop 多跳 | **20–40%** |
| Aggregation 聚合 | **15–30%** |
| Complex Reasoning 复杂推理 | **10–25%** |

极端情况（必须精确处理几乎所有位置的信息）可能只剩 **1–2%**（参考：[有效窗口比例表](https://iamkasong.com/course/a/h#tRB)；[极端情况](https://iamkasong.com/course/a/h#dnX)）。

### 解决办法：提前保存

核心思路是**在触达有效窗口上限前提前保存**。若同时使用 Grilling 优化策略，需求对齐可视为「简单检索」类型，极限约**宣称窗口的 70%**（参考：[解决办法](https://iamkasong.com/course/a/h#7pM)）。

三种情况（参考：[三种保存路径](https://iamkasong.com/course/a/h#RLp)）：

| 情况 | 做法 |
| --- | --- |
| **还没有模糊结论** | `/handoff` 总结已对齐细节到临时文档 → 手动 `compact` → 基于临时文档继续 |
| **已有模糊结论** | `/to-spec` 生成规格文档（讨论记录在其中）→ 手动 `compact` → 基于规格文档继续 |
| **需求太庞大**（一个缺口就填满有效窗口） | `/Wayfinder` 把缺口拆成多个 Issue，每个 Issue 一份规格文档，分别填补并在触达上限前保存 |

### 对实现侧无需处理

需求实现侧用 AFK，有目标、通过条件把控偏差。**长远看只需把控对齐侧的偏差，不让它传导到实现侧**；实现侧最终会退化为一句「实现已对齐的需求」（当前阶段更适合用 `/goal`）（参考：[对需求实现侧的影响](https://iamkasong.com/course/a/h#3oP)）。

# 第三部分：让实现变薄但可验证

## 第 19 节 · 关于测试用例（`a/i`）

### 重要前提

「实现侧退化为一句话」建立在一个假设上——**Agent 背后的模型足够聪明，实现的代码逻辑完全没问题**。若使用老旧模型，退化到 Superpowers 是更好的选择（参考：[假设前提](https://iamkasong.com/course/a/i#lpy)）。

### 为什么重要

长期迭代中，如何保证曾经的需求没被偏差破坏？只有两个途径：① 校验文档与实现是否一致；② 校验测试用例是否通过。① 需要投入 Agent 算力和运行时间，**只有 ② 是低成本、高效率的校验方式**（参考：[测试用例为什么重要](https://iamkasong.com/course/a/i#xMZ)）。

### 测试金字塔及其局限

| 测试类型 | 核心问题 | 典型范围 | 速度 | 真实度 |
| --- | --- | --- | --- | --- |
| Unit Test | 单个行为正确吗？ | 函数、类、模块、领域逻辑 | 最快 | 较低 |
| Integration Test | 部件协作正确吗？ | 数据库、API、消息、组件边界 | 中等 | 中等 |
| E2E Test | 完整用户流程能完成吗？ | 整个应用或业务链路 | 最慢 | 最高 |

传统比例是少量 E2E、适量集成、大量单元，整体呈金字塔。但**实际很难做到有效的测试金字塔，因为规划有效的测试用例需要消耗注意力**（参考：[测试金字塔](https://iamkasong.com/course/a/i#K1X)）。

### 难点：能否准确校验需求（重点）

难点不在测试用例本身，而在**测试用例能否准确校验需求**（参考：[测试用例的难点](https://iamkasong.com/course/a/i#kaj)）。

「VIP 购物 8 折」的例子（参考：[Agent 的实现](https://iamkasong.com/course/a/i#Q3m)）：

```ts
export function finalPrice(total: number, isVip: boolean) {
  return total - discount(total, isVip);
}
function discount(total: number, isVip: boolean) {
  return isVip ? total * 0.2 : 0;
}
```

Agent 为 `discount` 补一堆单元测试（VIP 优惠 20%、非 VIP 无优惠、总价 0 时优惠 0），覆盖率看起来很高。但**外部调用者实际调用的是 `finalPrice`**，它才是更能准确校验需求的测试对象（参考：[真正该测的对象](https://iamkasong.com/course/a/i#BQJ)）：

```ts
expect(finalPrice(100, true)).toBe(80);
expect(finalPrice(100, false)).toBe(100);
```

**内化要点**：很多 AI 主导的项目看似覆盖率高、比例也符合金字塔，实际上并不能准确校验需求，或者极度脆弱。Agent 不是不能自动生成准确的测试用例，而是**需要投入注意力**（参考：[覆盖率不等于验证需求](https://iamkasong.com/course/a/i#A0s)）。

### 最佳实践

**不刻意追求测试金字塔**，而是追求**关键路径被测试用例覆盖**，确保**测试用例能准确校验需求**（参考：[最佳实践](https://iamkasong.com/course/a/i#EQt)）。

## 第 20 节 · 三位一体开发流程（`a/j`）

### 核心结论

三位一体 = **TDD + Seam + Tracer Bullet**，用于实现「关键路径被测试覆盖、测试能准确校验需求」，这也是 Matt 需求实现侧使用的方式（参考：[三位一体开发流程](https://iamkasong.com/course/a/j#dI3)）。

### TDD：红绿重构，但要挑着用

红（先写会失败的测试）→ 绿（写刚好让测试通过的最简代码）→ 重构（在测试保护下优化）。两个好处：强迫写出**好用的代码**（测试先写，首要考虑「怎么被调用最舒服」，自然导出高内聚低耦合）；天然产出测试用例（参考：[TDD](https://iamkasong.com/course/a/j#bCM)）。

**但 AI 编程时两个好处都不再确切**：

1. 需求清晰时 Agent 编码质量已超过绝大多数开发者，不必为「写出好用的代码」强迫 TDD；反而**红绿重构三步会让实现变慢**
2. TDD 用好的核心前提是**测试用例写得足够好**。测试不能准确校验需求，红绿重构就没有意义。Superpowers 要求所有实现都走 TDD 却没把控好这个前提，于是产生大量「为了测试而测试」的无效测试

**所以 AI 编程下发挥 TDD 优势要满足两个条件**：① 只有关键步骤遵循 TDD，其余不强求；② TDD 的测试用例要能准确校验需求。

### Seam：最佳测试点

`Seam`（接缝）来自《Working Effectively with Legacy Code》。衣服上两块布料相接、可拆开替换重新缝合的位置就是 Seam；把布料理解为模块，**Seam 就是模块间可以替换、测试、隔离的连接点**（参考：[Seam](https://iamkasong.com/course/a/j#GSL)）。

在 VIP 8 折例子里，「先找到这个模块的 Seam，再在 Seam 上测试行为」→ Agent 会识别 **`finalPrice` 才是 Seam**。

**任务拆分上 Superpowers 与 Matt 最大的不同**：`/writing-plans` 拆的是**具体执行计划**，`/to-spec` 识别的是**需求中存在的 Seam**。

### Tracer Bullet：竖切

来自《The Pragmatic Programmer》（曳光弹）。夜间射击看不清弹道，曳光弹发光后可修正瞄准偏差。软件里指**竖切的开发策略**（参考：[Tracer Bullet](https://iamkasong.com/course/a/j#HeG)；[竖切](https://iamkasong.com/course/a/j#ULg)）。

做「用户上传文件 → 后端解析 → 存数据库 → 前端展示」：

- **横切**（Agent 默认）：依次实现 model → 解析逻辑 → API → 前端。坏处：反馈太晚（前端在最后）；容易做错抽象（先实现了后续层不一定会用的方法）；不容易做集成测试和 E2E 测试
- **竖切**（Tracer Bullet）：先打通一条很薄但完整的路径——上传一个最简单文件 → 后端读到一行 → 存一条最小记录 → 前端显示这一条。简陋，但竖切了所有层，后续实现都能在此延伸

### 总结：三者怎么合起来用

（参考：[总结](https://iamkasong.com/course/a/j#BIM)）

1. 对**已对齐的需求**，先识别出具体的 **Seam**
2. 把 **Seam 作为切口**，以 **Tracer Bullet** 模式识别出**完整的竖切流程**作为执行计划
3. **没有 Seam 的部分** → 用 Agent 默认开发模式（效率更高）
4. **有 Seam 的部分** → 用 **TDD**。因为 Seam 本身就是最佳测试点，在 Seam 上规划的 Tracer Bullet 正好就是**关键实现路径**

# 全章串讲：一条因果链

1. **为什么要编排**：单个任务的能力已解决，接下来是多个任务如何衔接（第 10 节）
2. **先看一个完整工作流**：Superpowers 把复杂度收进方法论，上手极低，代价是舍弃偏差把控（第 11 节）
3. **代价会兑现**：未填补的未知由 Agent 在实现时填补 → 过早细化 → 两层不对齐 → 每步都要审查纠偏 → 又慢又积累偏差（第 11、12 节）
4. **于是换思路**：Matt 把需求对齐做厚、需求实现做薄，并用 Issue 打通多人多 Agent（第 13 节）
5. **对齐怎么做**：Grilling 用设计决策树把每个需求缺口填成共同理解（第 14 节）
6. **对齐怎么不累**：四条优化——记录未知的已知、BFS 批量提问、按缺口类型分路、在上下文上限前保存（第 15–18 节）
7. **实现怎么守住**：不盯过程，盯测试用例能否准确校验需求（第 19 节）
8. **测试怎么来**：三位一体——用 Seam 定切口，用 Tracer Bullet 定关键竖切路径，在 Seam 上用 TDD（第 20 节）

贯穿始终的一条原则是**注意力与偏差的取舍**：Grilling 的四条优化全都在「保持完全对齐」前提下省注意力；三位一体则是「只在关键路径花注意力」。

<summary>参考要点</summary>

1. 因为 Skill 是自然语言写的，形式化与可判定性松散、难测试。**使用量大**降低效果不确定性；**结构简单**让你知道稳定效果来自哪；**模块化**让经受考验的原子 Skill 可重组。
2. ① 真实需求 ↔ 实现计划（Agent 自行填补未知）；② 实现计划 ↔ 实际代码（只有做到才知道）。设计文档审查治①，代码质量审查治②。
3. **偏差积累**。并行能补单任务慢，但 `brainstorming` 是用 AI 的已知填补人类的未知，正是偏差的主要来源，长期使用加速腐败。
4. Issue 是通用的进度／过程细节载体。自己与 Agent 交接用本地文档够；**多人类、多 Agent 交接**必须用平台 Issue，所以这是从流程编排迈向系统协同。
5. 优点：完全对齐、实现偏差少；缺点：消耗大量注意力。优化：记录未知的已知（`CONTEXT.md`／ADR）、BFS 批量提问、按缺口类型分路、触达窗口上限前保存（`/handoff`／`/to-spec`／Wayfinder）。
6. 分别记在 `CONTEXT.md`（统一语言）和 `ADR`（决策背景与代价）。不记目录结构和代码逻辑，因为 Agent 能快速查到且更新频繁、容易过时。记这两类是为了**概念完整性**。
7. DFS 一轮一个缺口、BFS 一轮一层前沿，轮次更少且不破坏依赖。另一个好处是**提供宏观视野、防止陷入局部需求缺口**——在缺口类型多样、需要选不同对齐策略时最关键。
8. 正确：`/handoff` 总结 → 开新 session 调研（Deep Research 或 HITL 学习）→ 结论 `/handoff` 带回 Grilling。错误：继续在 Grilling 里追问，因为那会陷入局部需求缺口。
9. 一来宣称窗口常虚标，二来有效窗口随任务复杂度下降：简单检索 50–70%，多跳 20–40%，聚合 15–30%，复杂推理 10–25%，极端只剩 1–2%。compact 丢失的是**已填补需求缺口的细节**，会经 Spec／Plan／Implement 被不断放大成偏差。
10. 外部调用者调用的是 `finalPrice`，不是 `discount`。`discount` 的测试只证明内部计算符合假设。应测 `finalPrice(100, true) === 80` 这类**对外行为**。
11. ① 需求清晰时 Agent 编码质量已很高，不必为「写出好用的代码」强迫 TDD，反而红绿重构三步变慢；② TDD 的前提是测试写得好，测试不准就没有意义。两个条件：只在关键步骤用 TDD；测试用例要能准确校验需求。
12. Seam 定**测试切口**（模块间可替换隔离的连接点），Tracer Bullet 定**执行计划**（竖切出完整关键路径），TDD 在 Seam 上**验证行为**。没有 Seam 的部分用 Agent 默认模式效率更高，强套 TDD 只会产生「为了测试而测试」。
