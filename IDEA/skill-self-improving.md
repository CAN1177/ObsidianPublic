# Skill Self-Improving

## 一句话定义

`skill-self-improving` 不是让 skill 自己“变聪明”，而是给 skill 外面增加一个**可验证、可归因、可回写**的优化闭环。

它的目标不是一次把 skill 写对，而是让 skill 在真实使用中持续收敛。

---

## 核心结论

一个 skill 想具备“自我进化”能力，至少要有 5 个组成部分：

1. 一个真正执行任务的 `inner skill`
2. 一组可以重复运行的真实样本
3. 一个能稳定判断结果好坏的 `grader`
4. 一个专门负责观察和归因的 `observer`
5. 一个安全的回写机制，而不是直接盲改 skill

如果缺少其中任何一个，这件事都容易退化成：

- 只是在聊天里讨论优化
- 靠模型主观判断“好像更好了”
- 改一次 skill，结果无法证明是否真的提升

---

## 本质结构

可以把它理解成一个双层系统：

### 内层

内层负责真正完成任务。

例如：

- 把网页迁移成代码项目
- 生成一段可运行代码
- 把原始数据抽取成结构化 JSON
- 把长文档转成符合规范的 Markdown
- 根据输入路由到合适的 workflow 步骤

### 外层

外层不直接完成业务任务，而是负责：

1. 观察内层输出
2. 验证结果
3. 发现失败模式
4. 归因问题来源
5. 生成改进建议或候选 diff
6. 再跑一轮验证改进是否有效

所以它不是“自我学习”，更准确地说是：

> **skill 的工程化优化闭环**

---

## 哪些 skill 适合做自我进化

不是所有 skill 都适合。

最关键的判断标准只有一个：

> **结果是否可验证**

### 适合的 skill 类型

#### 1. 代码生成类

例如：

- 生成接口调用代码
- 生成测试文件
- 生成脚手架

为什么适合：

- 能跑 `lint`
- 能跑 `typecheck`
- 能跑 `test`
- 是否通过非常明确

#### 2. 结构化转换类

例如：

- HTML 转 Markdown
- 文档转 JSON
- 表格抽取
- 配置格式转换

为什么适合：

- 能比对字段完整性
- 能检查格式合法性
- 能做 golden file 对比

#### 3. UI / 网页处理类

例如：

- 网页迁移
- 页面重构
- UI 自动生成

为什么适合：

- 能截图对比
- 能检查元素是否缺失
- 能用 browser/computer use 做交互验证

#### 4. 工作流路由类

例如：

- 判断当前任务处于哪个阶段
- 决定下一步调用哪个子 skill
- 判断是否允许进入下一阶段

为什么适合：

- 可以检查是否误路由
- 可以检查是否漏掉关键 Gate
- 可以检查是否在错误时机宣称完成

---

## 哪些 skill 不适合直接做自我进化

以下类型不适合一开始就自动化优化：

### 1. 创意写作类

例如：

- 文案润色
- 创意标题生成
- 风格化表达

问题：

- 很难定义稳定的自动评分标准

### 2. 方案脑暴类

例如：

- 讨论技术方案
- 给出产品方向建议
- 战略判断

问题：

- 没有确定的标准答案
- 过度自动优化容易把结果推向“保守但平庸”

### 3. 高主观性的审阅类

例如：

- 品牌文风审核
- 高层设计取舍判断
- 管理类建议

问题：

- grader 很难稳定
- observer 最后往往只能做主观评价

---

## skill 自我进化真正依赖的 5 个前提

## 1. 可进化对象

首先要明确你优化的是哪一个 skill。

它必须满足：

- 任务边界清楚
- 输入输出比较稳定
- 结果可验证

如果 skill 本身目标太模糊，后面所有环节都会失真。

## 2. 样本集

不能只拿一个案例跑。

至少需要 3 类样本：

### 成功样本

用来确认 skill 在正常场景下是否已经稳定。

### 失败样本

用来定位明显缺陷。

### 边界样本

用来发现规则的覆盖盲区。

没有样本集，所谓“进化”通常只是对单次案例的过拟合。

## 3. Grader

这是整个系统最关键的一层。

grader 负责回答：

> 这次输出到底好不好？

grader 可以非常朴素，不一定一开始就复杂。

例如：

- 是否通过构建
- 是否通过测试
- 是否字段齐全
- 是否存在 UI 缺失
- 是否漏掉关键步骤
- 是否违反既定约束

如果没有 grader，observer 只能做主观评论，系统就不成立。

## 4. Observer

observer 是外层 skill。

它不直接做业务任务，而是做：

1. 跑样本
2. 读取 trace
3. 调 grader
4. 聚合失败模式
5. 输出改进建议
6. 生成候选 patch 或 diff

可以理解为：

> `observer` 是 skill 的测试工程师 + 诊断工程师

## 5. 安全回写机制

第一阶段不要让系统直接自动改线上 skill。

更稳的方式是：

- 输出 `improvement_report.md`
- 输出 `suggested_diff.md`
- 输出 `suggested_patch`
- 人工 review 后再合并

否则很容易出现：

- skill 越改越窄
- 对少量样本过拟合
- 为了通过 grader 而牺牲泛化能力

---

## 推荐的最小实现路径

如果后面要做 `skill-self-improving`，最稳的第一版不是“自动修改 skill”，而是：

> **trace collection + grading + failure clustering + suggested diff**

也就是：

1. 收集运行轨迹
2. 用 grader 判断结果
3. 把失败模式聚类
4. 生成改进建议
5. 生成候选 diff
6. 人工确认是否采纳

这已经足够形成一个真正有价值的外层闭环。

---

## 一个通用的运行流程

```text
输入一批样本
    ↓
调用 inner skill 执行
    ↓
收集输出、日志、结果
    ↓
grader 打分 / 验证
    ↓
observer 聚合失败模式
    ↓
生成 improvement report
    ↓
生成 suggested diff / patch
    ↓
人工 review
    ↓
更新 skill
    ↓
重新跑样本验证是否提升
```

这才是“skill 自我进化”的最小可落地版本。

---

## 为什么不能一开始就自动改 skill

因为一开始最容易出现的不是“不会优化”，而是“优化错方向”。

常见风险有 3 类：

### 1. 过拟合

skill 为了通过这批样本，被改得只适合当前案例。

### 2. 局部最优

系统会不断做小修小补，但始终跳不出一个“还可以但不够好”的状态。

### 3. 假提升

grader 本身设计不完整，导致系统只是在“迎合评分”，而不是真的提升能力。

所以第一版一定要保留：

- 人工 review
- 回滚能力
- 固定样本对比

---

## 更合理的分阶段目标

### 阶段 1：可观测

先做到：

- 每次运行有 trace
- 每次结果能评分

### 阶段 2：可归因

再做到：

- 能区分失败类型
- 能找出重复问题

### 阶段 3：可建议

再做到：

- 能输出改进报告
- 能给出候选 patch

### 阶段 4：半自动进化

再做到：

- 人工审核后自动合并

### 阶段 5：受控自动化

最后才考虑：

- 在低风险 skill 上做自动更新

---

## 一个更通用的 observer 输出格式

建议后续把 `skill-self-improving` 的输出固定成这种结构：

```md
# Improvement Report

## Target Skill
[skill 名称]

## Sample Summary
- 总样本数：
- 成功：
- 失败：
- 边界异常：

## Failure Patterns
- 模式 1：
- 模式 2：
- 模式 3：

## Root Cause Guess
- 触发描述过窄
- 缺少边界规则
- 缺少验证步骤
- 输出格式不稳定
- 路由逻辑不清

## Suggested Changes
- 修改 description
- 补充规则
- 增加验证约束
- 增加失败回环
- 增加示例

## Suggested Diff
[候选 patch 或 diff]

## Risk
- 是否可能过拟合
- 是否影响已有成功样本
```

---

## 最后收敛

如果后面要真正实现 `skill-self-improving`，核心不要理解成：

- “让 AI 自动改自己的 prompt”

而应该理解成：

- “把 skill 变成可测试、可评分、可回归、可迭代的软件资产”

所以它的本质更接近：

> **skill 的自动化测试与持续优化系统**

而不是神秘的自我学习能力。

---

## 最适合的第一版定义

如果现在要给后续实现下一个明确结论，最合适的是：

> **`skill-self-improving` v1 = observer skill + grader + trace + suggested diff + human review**

不要一开始就追求全自动改 skill。

先把“观察、验证、归因、建议”做扎实，后续自动化才有意义。
